# Спецификация MVP: справочный чат-бот онкодиспансера

Статус: черновик v0.1 (до согласования с заказчиком).
Источник требований: страница проекта «Минздрав: чат-бот с ИИ-агентом для онкодиспансера» и документ «Чат бот для онкодиспансера».

## 1. Цель

Справочный чат-бот, который помогает пациентам и родственникам найти проверенную информацию на сайте и в утверждённых материалах учреждения и при необходимости передаёт вопрос специалисту.

Бот **не** назначает лечение, **не** ставит диагнозы, **не** работает с персональными данными.

## 2. Границы MVP

**Входит:**
- справочные ответы из утверждённой базы знаний (FAQ);
- поиск по утверждённым страницам сайта учреждения;
- обязательный источник для каждого ответа;
- правила безопасности (блокировка медицинских назначений и экстренных ситуаций);
- кнопка «Передать специалисту» — создаёт обращение в очередь;
- страница оператора для просмотра обращений и ответа на них;
- веб-виджет чата.

**Не входит (бэклог):**
- запись на приём, расписание, отмена и перенос (нужна интеграция с МИС);
- личные результаты анализов и выписки (персональные данные, авторизация);
- авторизация через ЕСИА/Госуслуги;
- мобильное приложение (Android) и мессенджер MAX;
- ИИ-генерация ответов.

Группы вопросов из подробного документа заказчика:
- группы 3, 5, 6, 7, 8 — статическая справочная информация, включаются в базу знаний после утверждения;
- группа 4 — только определения терминов и общие сведения; советы «что делать при симптомах» только по утверждённым текстам;
- группы 1, 2 — в бэклог (персональные данные и интеграции). Общие вопросы из них («какие документы нужны») могут войти как FAQ.

## 3. Роли

- **Пациент / родственник** — задаёт вопросы в виджете.
- **Оператор / врач** — видит обращения и отвечает на них.
- **Администратор базы знаний** (со стороны заказчика) — утверждает записи.

## 4. Функциональные требования

| ID | Требование |
|---|---|
| F1 | Бот принимает текстовый вопрос и возвращает утверждённый текст ответа из базы знаний. |
| F2 | Каждый ответ содержит источник: ссылку на страницу сайта или название документа. |
| F3 | Поиск учитывает формы слов русского языка (лемматизация). |
| F4 | Если подходящей записи нет, бот сообщает об этом и предлагает передать вопрос специалисту. |
| F5 | Правила безопасности срабатывают **до** поиска: вопросы о дозировках, приёме лекарств, диагнозе, экстренных симптомах получают фиксированный ответ с рекомендацией обратиться к врачу. |
| F6 | Кнопка «Передать специалисту» создаёт обращение с текстом диалога (без лишних персональных данных). |
| F7 | Страница оператора показывает список обращений, переписку и позволяет ответить. |
| F8 | Все тексты ответов берутся только из утверждённых записей. Запись без статуса «утверждено» не выдаётся. |

## 5. Нефункциональные требования

- Язык интерфейса — русский.
- Персональные данные: в MVP не запрашиваются. Логи не содержат ПДн; в тестах используются только синтетические данные.
- Хранение данных — в РФ (для прототипа — локально).
- Доступность для прототипа — не критична; для пилота потребуется отдельное требование.

## 6. Модель данных (черновик)

**Запись базы знаний (FAQ):**
- `id`, `question_variants` (список формулировок вопроса), `answer_text`, `source_url` или `source_doc`, `status` (`draft` / `approved`), `approved_by`, `approved_at`, `updated_at`.

**Обращение:**
- `id`, `created_at`, `dialog_text` (переписка), `status` (`new` / `in_progress` / `answered`), `answer_text`, `answered_at`.

## 7. Критерии приёмки

Из страницы проекта:
1. Бот корректно отвечает на согласованный набор тестовых вопросов.
2. Бот **всегда** показывает источник.
3. Бот **не** выдаёт медицинских назначений.
4. Бот предлагает обратиться к специалисту вне своей базы знаний.

Метрики для проверки:
- **Поиск:** доля тестовых вопросов, для которых правильная запись попала в top-3.
- **Безопасность:** доля тестовых вопросов с назначениями, на которые бот **не** выдал назначения (цель 100%).
- **Источники:** доля ответов с источником (цель 100%).

## 8. Тестовый набор

Файл `tests/questions.csv` (будет создан): вопрос, ожидаемая запись, ожидаемый источник, ожидаемое поведение (`answer` / `refuse` / `handoff`).

Набор формирует заказчик и эксперт. До его получения тестируем на собственных вопросах с пометкой «черновик».

## 9. Открытые вопросы к заказчику

1. Согласен ли заказчик с MVP только справочного бота без интеграций?
2. Можно ли индексировать страницы сайта учреждения, или нужен доступ через внутренний API?
3. Кто получает обращения специалистам, каким каналом и за какое время должен ответить?
4. Когда будет согласован тестовый набор и кто его утверждает?
5. В каком формате предоставляются обезличенные материалы?
6. Кто утверждает тексты и какой срок согласования?

## 10. Этапы

1. Спецификация и правила проекта (этот документ).
2. Тестовый набор вопросов (черновик).
3. Прототип: поиск по FAQ, правила безопасности, обращение, страница оператора.
4. Измерение метрик на тестовом наборе.
5. Согласование с заказчиком и демонстрация.
